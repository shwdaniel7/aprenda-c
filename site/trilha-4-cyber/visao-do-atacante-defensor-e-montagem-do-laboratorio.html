4.01

Visão do atacante × defensor e montagem do laboratório

Mentalidade ofensiva/defensiva + WSL2 ou VM prontos para o resto da trilha

Nível: Introdução/Cyber Duração: ~35 min Pré-requisitos: T0.01 (compilar e rodar no gcc), T0.02 (primeiros passos no gdb)

🎯 Objetivos

Entender o que um atacante (e um defensor) procura em código C, conhecer casos reais educacionais de referência e montar um laboratório Linux isolado (WSL2 ou VM) com gcc, gdb, valgrind, pwndbg e peda, criando a pasta labs/ para todos os exercícios da trilha.

📖 Leitura guiada

Foco da leitura: Use a trilha de intro-ctf do pwn.college (https://pwn.college/) para ver como desafios de pwn funcionam na prática, e o site do Exploit Education (https://exploit.education/) para conhecer os labs Phoenix/Protostar que usaremos nos módulos finais. Ambos são gratuitos, éticos e voltados a aprendizado.

Aviso ético e legal (leia antes de tudo)

Esta trilha trabalha com técnicas ofensivas de baixo nível: overflow, exploits, shellcode e redes. Isso é conhecimento necessário para defender — não existe defesa séria sem entender o ataque. Regra inegociável: rode APENAS em ambiente controlado (WSL2/VM isolada), nunca em produção, nunca em rede de terceiros, nunca contra um sistema sem autorização explícita por escrito do proprietário.

Todo exemplo desta trilha é didático: binários vulneráveis criados por você, para você, dentro de um diretório labs/. Não há malware real, exfiltração nem C2 real em nenhum bloco. Você vai gerar mini-exploits acadêmicos — os mesmos que as equipes de segurança (red team) e os pesquisadores (defesa) produzem nos seus estudos.

Ao terminar os exercícios, destrua ou isole os binários de exploração do seu sistema principal. Manter artefatos de exploit soltos por aí é má prática.

Duas visões, um mesmo código

A segurança de um software não é uma propriedade que se adiciona no final: ela nasce da forma como o programador trata entrada, memória e confiança. Veja o que cada lado enxerga no mesmo programa C:

  • Entrada não validada — o atacante procura a primeira linha que lê dado externo sem checar tamanho/conteúdo: gets, strcpy, scanf("%s"), printf(dado). O defensor procura exatamente os mesmos pontos para substituí-los por versões limitadas.
  • Memória — o atacante procura onde uma escrita pode estourar um buffer, corromper um ponteiro ou um endereço de retorno. O defensor procura as mesmas escritas para impor limites, canários e sanitização.
  • Confiança — o atacante procura o que o programa assume sobre o ambiente (variável de ambiente, banco de dados, arquivo de config, timeout). O defensor procura o que pode ser falsificado ou manipulado.
  • Superfícies de ataque — o atacante mapeia tudo que recebe bytes de fora; o defensor reduz esse mapa ao mínimo (menos entrada, menos privilégio, menos código exposto).

Estudos de caso (contexto educacional)

Conhecer falhas reais ajuda a entender por que esta trilha existe. Todos os casos abaixo são históricos e documentados — estudá-los é pesquisa acadêmica, não reprodução.

  • Morris Worm (1988) — um dos primeiros worms da internet explorou, entre outras falhas, um buffer overflow no fingerd (um serviço escrito em C que usava gets). O worm se propagou sozinho e derrubou grandes redes: um lembrete antigo de que uma única cópia sem limite de tamanho já era um problema em 1988.
  • Heartbleed (2014, CVE-2014-0160) — falha de bounds check na extensão heartbeat do OpenSSL (em C): o servidor copiava n bytes de um buffer sem conferir que existiam n bytes disponíveis, vazando memória do processo (incluindo chaves privadas). A lição: cheque o tamanho do dado contra o tamanho do alvo (bounds checking), nunca confie em um tamanho declarado pela entrada.
  • EternalBlue (2017) — falha em srv.sys do Windows (SMBv1, escrito em C) permitia escrever além do buffer no kernel. Combinado ao worm WannaCry, causou um dos maiores ataques de ransomware da história. Lição: exploração não é só brinquedo de aplicação — bugs de memória existem em nível de kernel.
  • Log4Shell (2021, CVE-2021-44228) — não é C (é Java/Log4j), mas mostra a versão moderna da mesma ideia: entrada não validada interpretada como código/conteúdo executável. O padrão mental "dado externo misturado com interpretação" é universal.

Por que C ainda é central em cibersegurança

Décadas depois, a maioria das vulnerabilidades sérias de memória (memory safety) vive em código C/C++: kernels, drivers, browsers, bibliotecas TLS/cripto, firmware de roteadores e sistemas embarcados. C domina justamente onde o hardware está perto: exploits, shellcode, análise de malware e engenharia reversa exigem C e assembly na veia.

A consequência prática para o curso: quem domina C entende (1) por que o bug existe, (2) como ele é explorável, (3) qual correção elimina a classe inteira, e (4) como ler relatórios (CVE, CWE, CVSS) sem panacéias. Ferramentas de scanner ajudam, mas a decisão final é humana.

Montando o laboratório com WSL2 + Ubuntu (recomendado)

No Windows, a maneira mais simples é o WSL2 com Ubuntu — você ganha um Linux real (kernel próprio) com terminal integrado. Passo a passo:

  • Abra o PowerShell como administrador e rode wsl --install (instala WSL2 + Ubuntu por padrão) e reinicie quando pedir.
  • Crie usuário/senha linux ao primeiro boot. Depois atualize: sudo apt update && sudo apt upgrade -y.
  • Instale as ferramentas: sudo apt install -y build-essential gcc gdb valgrind python3 netcat-openbsd tcpdump (build-essential traz gcc, make e libc).
  • (Opcional, recomendado para os módulos 4 a 7) Instale o pwndbg: git clone https://github.com/pwndbg/pwndbg, entre na pasta e rode ./setup.sh. Ele vira o gdb padrão com visualização de pilha e registradores.
  • (Alternativa) Instale o peda (já é um script único): git clone https://github.com/longld/peda, depois adicione source ~/peda/peda.py no final do seu ~/.gdbinit.
  • Crie a pasta de trabalho: mkdir -p ~/labs/4.{01..10} — um diretório por módulo. Os comandos desta trilha assumem que você está dentro de ~/labs.

Alternativa: máquina virtual isolada

Se preferir um isolamento mais forte que o WSL2 (ou não puder instalar o WSL), use uma VM:

  • VirtualBox (gratuito) + imagem Debian ou Kali. Kali já traz gdb, pwndbg, metasploit e ferramentas; Debian é mais enxuta e suficiente para esta trilha.
  • Configure a rede da VM como NAT ou rede interna — nunca "bridge" em rede de produção/terceiros. A VM deve estar isolada do resto da rede.
  • Instale as mesmas ferramentas da lista do WSL2 dentro da VM.
  • Vantagem extra da VM: snapshots. Tire um snapshot "limpo" antes de cada sessão de exploração e restaure depois — seu sistema base nunca é tocado.

Teste rápido do ambiente

Crie o programa abaixo dentro do WSL/VM e compile com o gcc do Linux. Se isto rodar, seu laboratório está pronto para o módulo 02. Este arquivo compila também no Windows/MinGW, mas esta trilha inteira assume o Linux.

Código — hello.c no Linux
#include <stdio.h>

int main(void)
{
    printf("Lab pronto: %d cores logicos\n", 1);
    printf("Este eh um Linux real, exigido pela trilha Cyber\n");
    return 0;
}
Saída esperada
$ gcc -Wall -Wextra -std=c11 hello_lab.c -o hello_lab
$ ./hello_lab
Lab pronto: 1 cores logicos
Este eh um Linux real, exigido pela trilha Cyber

Conferência do ambiente

Código — verificando as ferramentas
$ uname -a
$ gcc --version
$ gdb --version
$ valgrind --version
$ mkdir -p ~/labs && ls -ld ~/labs
Saída esperada
Linux DESKTOP-XXXX 5.15.xxx-microsoft-standard-WSL2 ...
gcc (Ubuntu 13.2.0-6ubuntu2) 13.2.0
GNU gdb (Ubuntu 13.2) ...
valgrind-3.19.0
drwxr-xr-x 2 voce voce 4096 ... labs

Regras de ouro para o resto da trilha

  • Rode APENAS em WSL2/VM controlada; nunca em produção — repita este mantra em cada módulo.
  • Os binários vulneráveis da trilha ficam somente em ~/labs. Não os copie para o sistema principal.
  • Desligue ASLR e use flags especiais de compilação SOMENTE durante o estudo, por sessão, e restaure ao final (veremos o comando exato no módulo 05).
  • Antes de explorar qualquer coisa, leia o código-fonte completo e escreva o que espera que aconteça. Exploração às cegas não é ciência.
  • Nenhum exercício requer contato com sistemas externos. Se algo pedir acesso a outra máquina, pare e revise: não é este material.

✏️ Exercícios

Nível 1

Exercício 4.01.1

Instale o WSL2 + Ubuntu (ou prepare uma VM com Debian/Kali), atualize o sistema e instale build-essential, gcc, gdb e valgrind. Rode uname -a, gcc --version e valgrind --version e confira que os três respondem.

Dica: Tudo isso é feito no terminal Linux. No WSL, use sudo apt install -y build-essential gcc gdb valgrind python3.

Ver solução
$ uname -a
Linux NC-DESKTOP 5.15.xxx-microsoft-standard-WSL2 #1 SMP ... x86_64 GNU/Linux
$ gcc --version
gcc (Ubuntu 13.2.0-6ubuntu2) 13.2.0
$ valgrind --version
valgrind-3.19.0

Se gcc não aparecer, rode sudo apt install -y build-essential. A versão exata não importa — precisa existir.

Nível 1

Exercício 4.01.2

Crie a estrutura de pastas ~/labs/4.01 até ~/labs/4.10 com um único comando e confirme com ls. Dentro de ~/labs/4.01 coloque o hello_lab.c desta seção, compile com -Wall -Wextra e rode.

Dica: Use mkdir -p ~/labs/4.{01..10} (expansão de chaves do bash).

Ver solução
$ mkdir -p ~/labs/4.{01..10}
$ ls ~/labs
4.01  4.02  4.03  4.04  4.05  4.06  4.07  4.08  4.09  4.10
$ cd ~/labs/4.01
$ gcc -Wall -Wextra -std=c11 hello_lab.c -o hello_lab
$ ./hello_lab
Nível 2

Exercício 4.01.3

Instale o peda (com o comando da seção) e confira que ele carrega: rode gdb ./seu_programa e dentro do gdb o prompt deve passar a mostrar as linhas de "PEDA". Depois digite quit.

Dica: Se o peda não carregar, verifique se a linha source ~/peda/peda.py está no fim do ~/.gdbinit e se o arquivo peda.py existe.

Ver solução
$ git clone https://github.com/longld/peda ~/peda
$ echo "source ~/peda/peda.py" >> ~/.gdbinit
$ gdb ./hello_lab
gdb-peda$ quit

A partir do módulo 04 usaremos peda/pwndbg diariamente para visualizar pilha e registradores.

❓ Verificação rápida

🏗️ Miniprojeto: Laboratório completo da trilha Cyber

Deixe o laboratório pronto para os módulos 02–10: WSL2 ou VM atualizada, gcc/gdb/valgrind/python3 instalados, peda E pwndbg (ou só um deles, mas configurado), pastas ~/labs/4.01..4.10 criadas, e um ~/notas_gdb.txt com os comandos essenciais do gdb que você já conhece da Trilha 0. Dentro de cada pasta labs/4.XX crie um README.md de uma linha descrevendo o que será estudado ali (pode escrever depois, conforme avança).

Critérios de aceite

  • uname -a, gcc --version, gdb --version e valgrind --version respondem no terminal Linux.
  • ~/labs/4.01…4.10 existem e a seção 4.01 contém o hello_lab compilado e rodando.
  • peda OU pwndbg carregam no gdb sem erro.
  • Você consegue abrir o gdb, carregar um binário, dar break, run e sair.
