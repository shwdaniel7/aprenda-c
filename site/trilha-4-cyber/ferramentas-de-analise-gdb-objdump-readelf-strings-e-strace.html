4.04

Ferramentas de análise: gdb, objdump, readelf, strings e strace

Instrumentar binários, ler assembly e rastrear syscalls

Nível: Avançado/Cyber Duração: ~45 min Pré-requisitos: T0.01 (gdb básico), T4.03 (anatomia da memória)

🎯 Objetivos

Dominar o conjunto de ferramentas do analista de binários: gdb a fundo (breakpoints, examinar memória/registradores, disassembly, watchpoints, find), peda/pwndbg, objdump (-d/-s), readelf, strings e strace — para dissecar um binário C compilado com -g e identificar seus frames e dados.

📖 Leitura guiada

Foco da leitura: Leia o manual do gdb (info gdb ou https://sourceware.org/gdb/current/onlinedocs/gdb/) com foco em "Examining Memory" e "Examining Data". Para o assembly, consulte a referência de instruções do System V AMD64 ABI e o README do pwndbg (https://github.com/pwndbg/pwndbg). A prática do módulo vale mais que a leitura: rode cada comando no seu binário.

O binário de estudo (compilado para análise)

Vamos trabalhar com um programa trivial compilado de forma a deixar o assembly didático: -g (símbolos), -fno-stack-protector e -no-pie (sem randomização do binário — endereços estáveis, mais fácil de acompanhar). Não use estes flags em código real: aqui são só para estudo. Este módulo roda inteiro no Linux/WSL (no MinGW o gdb é outra história); segue o programa:

Código — analise.c
/* analise.c -- alvo de estudo das ferramentas.
   gcc -g -fno-stack-protector -no-pie -Wall -Wextra analise.c -o analise */
#include <stdio.h>

static int soma(int a, int b)
{
    return a + b;
}

static void processa(const char *dado)
{
    char buf[16];
    snprintf(buf, sizeof buf, "%s", dado);
    puts(buf);
    (void) soma(2, 3);
}

int main(void)
{
    processa("reconhecimento");
    return 0;
}
Saída esperada
$ gcc -g -fno-stack-protector -no-pie -Wall -Wextra analise.c -o analise
$ ./analise
reconhecimento

gdb: breakpoints, stepping por instrução e registradores

O gdb é o microscópio. Os comandos desta seção cobrem 90% do uso em exploração:

  • break N ou break processa — pausa na linha N ou no início da função.
  • info registers (curto: i r) — mostra todos os registradores (RIP, RSP, RBP, RAX…).
  • x/20x $rsp — examina 20 words hexa a partir de RSP; x/20wx força 4 bytes/word, x/10gx 8 bytes. É o "x-ray" da pilha.
  • x/20xb $rsp — bytes avulsos (essencial para ver payload/thancle endianness).
  • nexti (ni) — executa UMA instrução de máquina; next (n) executa uma linha de C. stepi (si) entra em calls, ni não.
  • disas (disassemble) — mostra o assembly da função atual; disas processa de qualquer função.
  • watch var — para a execução quando a variável mudar de valor (watchpoint).
  • find /b 0x400000, 0x410000, 0x44, 0x45, 0x41 — procura uma sequência de bytes num intervalo de endereços.
Código — sessao gdb basica
gdb ./analise
(gdb) break processa
(gdb) run
(gdb) info registers rsp rbp rip
(gdb) disas
(gdb) x/16wx $rsp            # a frame inteira na tela
(gdb) ni
(gdb) ni
(gdb) info registers rip     # RIP avancou 2 instrucoes
(gdb) continue
(gdb) quit
Saída esperada

Encontrando o return address e o offset da frame

Técnica valiosa para os próximos módulos: marcar a pilha com um padrão e ler onde ele aparece. No gdb, escreva em memória uma marca e depois veja em que offset do buffer ela cai. Passo a passo (parada em processa após os locals):

Código — marcando a pilha
(gdb) break *processa+4        # apos sub $0x20 (frame montada)
(gdb) run
(gdb) set {long} $rsp = 0x4142434445464748   # "HGFEDCBA"
(gdb) x/8gx $rsp
0x7fffffffe3b0: 0x4142434445464748  0x0000000000000000
0x7fffffffe3c0: 0x0000000000000000  0x0000000000000000
0x7fffffffe3d0: 0x0000000000000000  0x00000000004011dd
                                          ^^^^^^^^^^ return address p/ main
(gdb) quit

peda e pwndbg: o gdb turbinado

Pedra e pwndbg são plugins do gdb que desenham a pilha, destacam o return address, decodificam endereços (text vs libc) e trazem comandos prontos. Com o pwndbg (preferido aqui):

  • checksec — mostra NX, PIE, canário, RELRO do binário carregado (o "checar blindagens" de cada exploração).
  • cyclic 100 (pwntools) — gera padrão para achar offset exato; cyclic -l 0x61616164 devolve o offset.
  • canary — tenta mostrar o canário da thread atual (módulos 06).
  • stack N — imprime N words da pilha com anotações; regs lista registradores em colunas.
  • O realce automático: o return address aparece na pilha com cor/rotulo "ret addr" — economiza horas de x/20x.
Código
$ gdb ./analise
pwndbg> checksec
    Arch: amd64-64-little
    RELRO: Partial RELRO
    Stack: No canary found
    NX: NX enabled
    PIE: No PIE (0x400000)
pwndbg> break processa
pwndbg> run
pwndbg> stack 12
00:0000│ rsp 0x7fffffffe3b0 ◂— 0x0
04:0020│     0x7fffffffe3d0 ◂— 0x4011dd  /* ret addr para main+0x14 */
...

objdump: o assembly sem executar

Para "ler" o binário sem abrir o gdb, o objdump desconstrói o arquivo:

  • objdump -d analise — desmonta o código de todas as funções para assembly (Intel com -M intel).
  • objdump -d -M intel analise | grep -A25 "<processa>" — só a função processa.
  • objdump -s -j .rodata analise — hexdump da seção de constantes (strings literais do seu programa).
  • objdump -t analise — tabela de símbolos (funções e endereços).
Código — objdump e readelf
$ objdump -d -M intel analise | grep -A25 "<processa>:"
<processa>:
   push   rbp
   mov    rbp,rsp
   sub    rsp,0x20
   lea    rax,[rip+0x2e9b]     # "reconhecimento"
   mov    rsi,rax
   mov    edi,0x20
   call   ...
   ...
$ readelf -h analise          # cabecalho ELF (tipo, entradas...)
$ readelf -S analise          # tabela de secoes (.text, .data, .rodata...)
$ readelf -s analise | grep -E "processa|main|soma"   # simbolos

strings e strace: pistas e comportamento

Duas ferramentas rápidas de inteligência:

  • strings binario — extrai todas as sequências de texto; strings -n 8 ignora as curtas. Em CTFs, o strings muitas vezes entrega a "flag" ou mensagens escondidas; em análise, revela mensagens de erro e paths que desenham o comportamento.
  • strace -f ./analise — registra cada syscall (read, write, mmap, execve, connect): mostra com que o programa fala, quando e com quais argumentos. Útil para perceber chamadas suspeitas (ex.: uma conexão de saída).
Código — strings e strace
$ strings analise | head
/lib64/ld-linux-x86-64.so.2
reconhecimento
...
$ strace ./analise 2>&1 | tail -20
execve("./analise", ...) = 0
brk(NULL) ...
write(1, "reconhecimento\n", 15) = 15
exit_group(0)

Como se defender

  • Use as mesmas ferramentas do atacante na sua defesa: checksec para confirmar que canário/NX/PIE/RELRO estão ativos no binário que você publica.
  • Leia o assembly do seu próprio código compilado com -O2 para confirmar que o compilador não introduziu chamadas estranhas (ou que suas funções de string segura não viraram código quente demais).
  • Rode strace em serviços próprios para auditar "com o que este processo conversa" (devem ser só os peers esperados).
  • Em incidentes, capture o core dump (ulimit -c) e analise com gdb: a pilha do crash é a primeira pista da causa raiz — exatamente como você aprendeu a "sentir" a pilha aqui.
  • Binários de produção devem passar por gvim readelf -d para checar dependências e por valgrind/ASan em testes.

✏️ Exercícios

Nível 2

Exercício 4.04.1

Compile analise.c com -g -fno-stack-protector -no-pie e, no gdb, coloque breakpoint em processa. Imprima info registers rbp rip, depois x/20x $rsp e x/1gi $rip. Identifique o return address na pilha (o ponteiro que aponta para a instrução seguinte ao call em main).

Dica: Monte a frame (Pressione run para parar no break; dê ni umas 3 vezes). A pilha é little-endian: o ret vem em gx com os bytes na ordem inversa.

Ver solução
$ gdb ./analise
(gdb) break processa
(gdb) run
(gdb) i r rbp rip
rbp            0x7fffffffe3c0      0x7fffffffe3c0
rip            0x4011b0            0x4011b0 <processa>
(gdb) x/20x $rsp
0x7fffffffe3b0: ... ...
(gdb) x/1i $rip
=> 0x4011b0 <processa>: push %rbp

O ret addr fica no endereço rbp+8: x/gx $rbp+8. Na dúvida, siga o endereço retornado com x/3i para conferir que é código de main.

Nível 3

Exercício 4.04.2

Use o gdb para quebrar em um campo específico da frame: pare em processa, avance 4 instruções (ni 4x), escreva o valor 0x41 (quatro A) em $rbp+8 (set {long} $rbp+8 = 0x41414141) e continue. O que acontece? Explique por que o gdb reporta o que reporta.

Dica: Ao dar leave; ret, a CPU vai pular para 0x41414141 — fora do mapa do processo.

Ver solução
(gdb) ni 4
(gdb) set {long} $rbp+8 = 0x41414141
(gdb) continue
Continuing.
Program received signal SIGSEGV, Segmentation fault.
0x0000000000414143 in ?? ()
Cannot access memory at address 0x41414141

RIP tentou ir para 0x41414141 (little-endian) e o kernel abortou. Isso é literalmente o que o módulo 05 fará com um endereço de verdade.

Nível 2

Exercício 4.04.3

Com o objdump, liste o assembly completo de main e de processa. Identifique no main a instrução call que invoca processa e o endereço da instrução seguinte (o ret address). Confirme com objdump -t os endereços das três funções.

Dica: No assembly Intel: o call aparece seguido do leave/ret; o endereço apontado pelo RIP após o call é o ret address.

Ver solução
$ objdump -d -M intel analise | sed -n '/<main>:/,/<_fini>:/p'
00000000004011e0 <main>:
   ...
  call   4011b0 <processa>
   ...
  call   401160 <soma+0x...>   # ver simbolos
$ objdump -t analise | grep -E " main| processa| soma"

❓ Verificação rápida

🏗️ Miniprojeto: Cartão de análise de um binário

Compile o analise.c com flags reais (-O2 -fstack-protector-all -pie) e com o flag de estudo (-O0 -fno-stack-protector -no-pie), e monte um cartão comparativo em markdown: para cada binário registre (a) checksec (NX, PIE, canário, RELRO), (b) endereço de main e de processa no objdump -t, (c) o endereço do buffer dentro de processa em 2 execuções (mudou? por quê?), (d) se o return address está a offset fixo do buffer. Feche com a pergunta: "em qual dos dois binários um overflow de buffer controlaria o fluxo com mais facilidade?"

Critérios de aceite

  • Dois cartões (um por build) com NX/PIE/canário/RELRO registrados.
  • Endereços de main/processa e do buffer, com a variação (ou não) entre execuções explicada.
  • Offset buffer→return address medido no gdb.
  • Conclusão comparando a dificuldade de exploração nas duas builds.
