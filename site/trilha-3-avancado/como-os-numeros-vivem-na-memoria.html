complemento de 2, IEEE 754, NaN/Infinity e sizes

Inteiros e o complemento de 2

Praticamente todos os processadores modernos representam inteiros negativos em complemento de 2: o negativo de um número é ~x + 1 (inverte todos os bits e soma 1). Isso faz com que a soma x + (~x + 1) vire exatamente zero sem lógica especial, e que o bit mais significativo funcione como sinal. Consequências práticas: a faixa é assimétrica (num int de 32 bits vai de -2147483648 a 2147483647), estouro de sinal é um undefined behavior teórico (embora na prática ele "dê a volta"), e INT_MIN é o único cujo negativo não cabe.

  • Em complemento de 2, ~x + 1 é sempre igual a -x — teste no exercício 2.
  • O bit mais à esquerda = 0 para positivos, 1 para negativos.
  • Somador de hardware não diferencia positivo/negativo: a matemática "simplesmente funciona".
  • Nunca desloque um valor negativo para a direita esperando o sinal se propagar — comportamento de implementação.

Lendo os bits de um float

Um float IEEE 754 de 32 bits divide-se em três campos: 1 bit de sinal, 8 bits de expoente (com viés de 127) e 23 bits de mantissa (a fração binária, com um 1 implícito). O valor é ±1.fração × 2^(expoente−127). O truque clássico para inspecionar os bits é uma union que enxerga os mesmos 4 bytes como float ou como uint32_t.

Código — bits.c
#include <stdio.h>
#include <stdint.h>

static void bits_float(float f)
{
    union {
        float f;
        uint32_t u;
    } conv;
    conv.f = f;
    printf("%10g = ", (double)f);
    for (int i = 31; i >= 0; i--) {
        putchar((conv.u >> i) & 1u ? '1' : '0');
        if (i == 31 || i == 23) {
            putchar(' ');
        }
    }
    putchar('\n');
}

int main(void)
{
    bits_float(1.0f);
    bits_float(0.5f);
    bits_float(-2.5f);
    return 0;
}
Saída esperada
> bits
         1 = 0 01111111 00000000000000000000000
       0.5 = 0 01111110 00000000000000000000000
      -2.5 = 1 10000000 01000000000000000000000

Por que 0.1 é inexato

Assim como 1/3 não tem representação finita em decimal, 0.1 em binário é uma dízima periódica. Então 0.1 guardado num double é o "mais próximo representável" — e não o 0.1 exato. Somar dez vezes esse valor não devolve 1.0, e 0.1 + 0.2 não é 0.3. Isso não é bug do C: é a natureza do ponto flutuante. A comparação correta usa uma tolerância (ex.: fabs(a - b) < 1e-9).

Código — inexato.c
#include <stdio.h>

int main(void)
{
    double soma = 0.0;
    for (int i = 0; i < 10; i++) {
        soma += 0.1;
    }
    printf("soma = %.20f\n", soma);
    printf("soma == 1.0? %s\n", soma == 1.0 ? "sim" : "NAO");
    printf("1.0 - soma = %.20g\n", 1.0 - soma);
    double a = 0.1 + 0.2;
    printf("0.1 + 0.2 = %.20f\n", a);
    printf("0.1 + 0.2 == 0.3? %s\n", a == 0.3 ? "sim" : "NAO");
    return 0;
}
Saída esperada
> inexato
soma = 0.99999999999999988898
soma == 1.0? NAO
1.0 - soma = 1.1102230246251565404e-16
0.1 + 0.2 = 0.30000000000000004441
0.1 + 0.2 == 0.3? NAO

NaN e Infinity: os valores especiais

O IEEE 754 reserva valores de expoente para representar infinito e não-número (NaN). Dividir por zero dá inf (ou -inf); 0.0/0.0 dá NaN. A macro isfinite de <math.h> testa se o número é finito, e isnan testa NaN. A regra de ouro: NaN nunca é igual a nada, nem a ele mesmo — nan == nan é falso. É por isso que você testa com isnan e não com ==.

Código — especiais.c
#include <stdio.h>
#include <math.h>

int main(void)
{
    double inf = 1.0 / 0.0;
    double nan = 0.0 / 0.0;
    printf("1.0/0.0 = %g\n", inf);
    printf("0.0/0.0 = %g\n", nan);
    printf("inf e finito? %s\n", isfinite(inf) ? "sim" : "nao");
    printf("nan e NaN? %s\n", isnan(nan) ? "sim" : "nao");
    printf("inf == inf? %s\n", inf == inf ? "sim" : "nao");
    printf("nan == nan? %s\n", nan == nan ? "sim" : "nao");
    return 0;
}
Saída esperada
> especiais
1.0/0.0 = inf
0.0/0.0 = -nan(ind)
inf e finito? nao
nan e NaN? sim
inf == inf? sim
nan == nan? nao

sizeof, limits.h e a verdade das plataformas

O C garante faixas mínimas, não tamanhos exatos. O mesmo código compilado em Windows e Linux pode mudar: no Windows (modelo LLp64) long tem 4 bytes; no Linux (LP64) long tem 8 bytes. int, float e double costumam ser 4/4/8 em ambos, mas você nunca deve confiar — confie em sizeof e nas constantes de <limits.h>/<float.h>. Para inteiros com tamanho garantido use os tipos de <stdint.h> (int32_t, int64_t).

Código — sizes.c
#include <stdio.h>
#include <limits.h>
#include <float.h>

int main(void)
{
    printf("char:     %2zu bytes  (%d ate %d)\n", sizeof(char), CHAR_MIN, CHAR_MAX);
    printf("int:      %2zu bytes  (%d ate %d)\n", sizeof(int), INT_MIN, INT_MAX);
    printf("long:     %2zu bytes  (%ld ate %ld)\n", sizeof(long), LONG_MIN, LONG_MAX);
    printf("long long:%2zu bytes  (%lld ate %lld)\n", sizeof(long long), LLONG_MIN, LLONG_MAX);
    printf("float:    %2zu bytes  (epsilon ~%g)\n", sizeof(float), FLT_EPSILON);
    printf("double:   %2zu bytes  (epsilon ~%g)\n", sizeof(double), DBL_EPSILON);
    printf("ponteiro: %2zu bytes\n", sizeof(void *));
    return 0;
}
Saída esperada
> sizes     (Windows / MinGW 64 bits)
char:      1 bytes  (-128 ate 127)
int:       4 bytes  (-2147483648 ate 2147483647)
long:      4 bytes  (-2147483648 ate 2147483647)
long long: 8 bytes  (-9223372036854775808 ate 9223372036854775807)
float:     4 bytes  (epsilon ~1.19209e-07)
double:    8 bytes  (epsilon ~2.22045e-16)
ponteiro:  8 bytes

✏️ Exercícios

Nível 2

Exercício 3.02.1

Escreva um programa que guarda o uint32_t 0x01020304 na memória e imprime os 4 bytes em ordem de endereço. Com base na saída, diga se a máquina é little-endian ou big-endian.

Dica: Faça um cast de unsigned char* sobre o endereço do inteiro e imprima p[0], p[1], p[2], p[3].

Ver solução
#include <stdio.h>
#include <stdint.h>

int main(void)
{
    uint32_t x = 0x01020304u;
    unsigned char *p = (unsigned char *)&x;
    printf("bytes em memoria: %02x %02x %02x %02x\n", p[0], p[1], p[2], p[3]);
    if (p[0] == 0x04) {
        printf("little-endian (x86, x86-64)\n");
    } else if (p[0] == 0x01) {
        printf("big-endian\n");
    } else {
        printf("ordem inesperada\n");
    }
    return 0;
}

Saída neste computador (x86-64): "bytes em memoria: 04 03 02 01" e "little-endian". O byte menos significativo vem primeiro.

Nível 1

Exercício 3.02.2

Prove em C que ~x + 1 == -x para vários valores (0, 1, -1, 42, -42, 100000, -100000) e imprima a comparação para cada um.

Dica: Use um array de ints e um loop; compare (~x + 1) == -x.

Ver solução
#include <stdio.h>

int main(void)
{
    int vals[] = {0, 1, -1, 42, -42, 100000, -100000};
    for (size_t i = 0; i < sizeof vals / sizeof vals[0]; i++) {
        int x = vals[i];
        int neg = ~x + 1;
        printf("x=%7d  ~x+1=%7d  igual a -x? %s\n", x, neg,
               neg == -x ? "sim" : "nao");
    }
    return 0;
}

Saída real: para todos os valores testados a igualdade é "sim" — é o complemento de 2 funcionando.

Nível 3

Exercício 3.02.3

Escreva um "decodificador de float": com uma union, leia os bits de um float, extraia sinal, expoente e mantissa, e reconstrua o valor ±(1.fração) × 2^(expoente−127) usando ldexp. Use -13.25f como caso de teste.

Dica: A fração é a mantissa lida do bit 22 ao bit 0: se o bit k está ligado, soma ldexp(1.0, -(k+1)) à fração (que começa em 1.0).

Ver solução
#include <stdio.h>
#include <stdint.h>
#include <math.h>

int main(void)
{
    union {
        float f;
        uint32_t u;
    } c;
    c.f = -13.25f;
    uint32_t u = c.u;
    unsigned sinal = u >> 31;
    unsigned expo = (u >> 23) & 0xffu;
    uint32_t mant = u & 0x7fffffu;

    double fracao = 1.0;
    for (unsigned i = 0; i < 23; i++) {
        if (mant & (1u << (22 - i))) {
            fracao += ldexp(1.0, -(int)(i + 1));
        }
    }
    double valor = ldexp(fracao, (int)expo - 127);
    if (sinal) {
        valor = -valor;
    }

    printf("bits: %08x\n", (unsigned)u);
    printf("sinal=%u expoente=%u mantissa=%06x\n", sinal, expo, (unsigned)mant);
    printf("valor decodificado = %.6g\n", valor);
    return 0;
}

Saída real: bits: c1540000 / sinal=1 expoente=130 mantissa=540000 / valor decodificado = -13.25. Expoente 130−127 = 3 e 1.65625×2³ = 13.25.

❓ Verificação rápida

🏗️ Miniprojeto: Dump de arquivo em hex e binário

Crie hexdump.c: dado um arquivo (ex.: um .txt pequeno), imprime cada byte como hex (offset de 4 dígitos + 16 bytes em hex + os bytes legíveis ao lado). No fim, mostre a contagem de bytes que são ASCII imprimível e a dos que pertencem a sequências multibyte (bit 7 ligado). É o início do seu "olho de baixo nível" — útil para a Trilha 4.

Critérios de aceite

  • Compila com gcc -Wall -Wextra -std=c11 sem avisos.
  • Para o arquivo numeros.txt (3 linhas), imprime o offset inicial 0000 e todos os bytes em hex.
  • A última coluna mostra os caracteres ASCII legíveis e ponto (.) para os demais.
  • Relatório final: total de bytes, ASCII imprimíveis e bytes com bit 7 ligado.
  • Trata erro de abertura com strerror e EXIT_FAILURE.
